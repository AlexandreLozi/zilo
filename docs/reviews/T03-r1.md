## Findings

### 1. High — shared intermediate apphost breaks macOS architecture publishing

**Paths:** `packaging/publish.sh:23–29,36–41`; `docs/spikes/SP-4a.md:29,70–71`;
`docs/validation/logs/T03/publish-osx.log:20–22`.

Changing only `DefaultAppHostRuntimeIdentifier` while reusing the same project intermediate
directory does not reliably recreate `obj/Release/net10.0/apphost`. On a fresh checkout,
publishing arm64 then x64, exactly as the macOS branch does, produced **two identical arm64
Mach-O apphosts**. Thus `lipo -create` cannot create the required two-architecture binary.
This is a build-time defect, independently observable on Linux. The existing hosted macOS
run independently confirms it: `lipo` reports that both inputs have architecture arm64.

There is also cross-target contamination: running the actual Linux build, Windows publish,
then actual `packaging/publish.sh osx ...` produced an **ELF linux-x64** executable in the
macOS output. The author log's 78192-byte output matches the Linux apphost size seen here;
the log does not establish the claimed arm64 apphost.

**Executed reproduction**, SDK 10.0.403, separate clean archive checkout:

```sh
for rid in osx-arm64 osx-x64; do
  dotnet publish backend/src/Zilo.Agent/Zilo.Agent.csproj --configuration Release \
    -p:RestoreLockedMode=true -p:PublishSingleFile=false -p:PublishTrimmed=false \
    -p:DebugType=none -p:GenerateDocumentationFile=false \
    -p:DefaultAppHostRuntimeIdentifier="$rid" -o "$scratch/$rid"
done
file "$scratch"/osx-{arm64,x64}/Zilo.Agent
sha256sum "$scratch"/osx-{arm64,x64}/Zilo.Agent
```

Both files: `Mach-O 64-bit arm64 executable`; both SHA-256:
`bad7f6862fa7404877c3d694d15cd8ef75c06fe7397df63955ec198057680e4e`.

**Requested correction:** isolate/rebuild the native apphost for each target, assert its
format/architecture before merging, and test both clean macOS publishing and publishing
after another target. Correct the report's arm64 evidence claim; the hosted pkg build failed
despite the green job status (finding 6). RID/lock policy changes require master approval,
not disabling locked restore as a workaround.

### 2. High — Windows CI resolves its publish input from the wrong directory

**Paths:** `packaging/windows/build-msi.ps1:16–24`;
`.github/workflows/packaging-dryrun.yml:120,125–126`.

The workflow publishes into repository-root `artifacts/publish-win` and passes that relative
path to the PowerShell builder. The builder first executes `Push-Location $here` (the
`packaging/windows` directory), then calls `Resolve-Path $PublishDir`. It therefore looks for
`packaging/windows/artifacts/publish-win`, which was never created, instead of the workflow's
actual output. With `$ErrorActionPreference = 'Stop'`, this blocks the MSI build even on a
hosted runner. This is separate from the honestly reported Linux WiX/platform limitation.

**Evidence:** inspected the call order and evaluated the two paths with Python `pathlib`;
they differ. Existing hosted run `41240014938`, Windows job `124651784286`, confirms
`Cannot find path 'D:\a\zilo\zilo\packaging\windows\artifacts\publish-win' because it does
not exist` at `build-msi.ps1:22`. No PowerShell, WiX, installer or Windows binary was run
on the owner's host by this review.

**Requested correction:** resolve caller-relative inputs/outputs before changing location,
or pass absolute paths from the workflow, and cover the exact root-relative invocation.
Do not call the hosted workflow ready until this path contract is corrected.

### 3. Medium — uninstall recursively deletes the shared vendor registry namespace

**Paths:** `packaging/windows/Zilo.Agent.wxs:35,46`;
`packaging/windows/install-smoke.ps1:52`.

The MSI owns the marker under `HKCU\Software\Zilo\Agent`, but explicitly removes the entire
`HKCU\Software\Zilo` tree on uninstall. That can delete settings belonging to another Zilo
component/product or an existing sibling key. The smoke currently reinforces that overbroad
deletion by demanding that the entire vendor namespace disappear.

**Evidence:** XML inspection of the owned key and `RemoveRegistryKey Action="removeOnUninstall"`
target. Actual Windows behavior remains unexecuted under OD-6.

**Requested correction:** remove only resources owned by this package, and extend hosted
install/uninstall evidence with a pre-existing sibling sentinel that must survive. Keep the
per-user HKCU/LocalAppData design; this is not a request to switch to machine-wide installation.

### 4. Medium — rpm verification failure is not fatal to the smoke

**Path:** `packaging/linux/smoke/rpm-smoke.sh:43`.

`rpm -V zilo-agent && echo "rpm -V: clean"` puts the verification on the left side of an AND
list. Under `set -e`, a failed verification does not stop the script; later steps can still
print `RPM SMOKE PASS`. Mode/ownership/content drift that does not break the narrow agent
output check can therefore be missed. The actual author log does show a successful clean
verification; this finding is about future acceptance reliability, not falsifying that log.

**Executed shell control-flow reproduction:**

```sh
sh -ec 'false && echo "rpm -V: clean"; echo "continued after failed rpm verification"'
# prints the continuation and exits 0
```

**Requested correction:** explicitly fail on a nonzero verification status, with a negative
control proving the smoke cannot pass when verification detects a changed file/mode.

### 5. Medium — workflow does not preserve the requested osslsigncode pin

**Paths:** `.github/workflows/packaging-dryrun.yml:49–52`;
`docs/spikes/SP-4a.md:125–128`; `docs/tasks/T03.md` step 2.

The local log records `osslsigncode` 2.8-2 and its archive SHA-256, but the workflow uses an
unversioned `apt-get install osslsigncode`. Its future signing-smoke implementation is whatever
the mutable Ubuntu archive serves, rather than the pinned tool required by the task. The
same workflow also leaves wixl/rpm versions floating. In contrast, nfpm is explicitly pinned
and hash-checked, and the WiX manifest specifies exactly 5.0.2.

**Requested correction:** reproducibly select/verify the approved signing tool version and
artifact provenance in CI, or explicitly obtain a master-approved deviation rather than
describing the local version log as a durable workflow pin. No host package installation is
needed to make this change.

### 6. High — workflow tee pipelines report success when package builds fail

**Paths:** `.github/workflows/packaging-dryrun.yml:54–68,153–156,157–164`.

The POSIX build steps do not specify `shell: bash` or enable `pipefail`. The runner's
unspecified-shell invocation uses `bash -e`, so `packaging/... | tee ...` returns tee's
success even if the producer exits nonzero. The macOS hosted job demonstrates the resulting
false pass: `lipo` fatally rejects the duplicate arm64 inputs, yet the build step/job report
success. Upload also succeeds because the log alone matches the combined artifact paths;
the resulting macos-pkg artifact is just 588 bytes, not a built installer.

**Evidence:** existing run `41240014938`, macOS job `124651784109`, log at
`2026-10-31T20:40:51.6700220Z` reports `have the same architectures (arm64) and can't be in
the same fat output file`; the job conclusion is `success`. No `pkgbuild`/`productbuild`
completion appears. The same exit-masking pattern covers Linux build/inspection/signing.
Local reproduction: `bash -ec 'false | tee /dev/null'` exits zero.
The actual hosted log confirms `shell: /bin/bash -e {0}` and
`Artifact macos-pkg has been successfully uploaded! Final size is 588 bytes`;
[artifact 13056783268](https://github.com/AlexandreLozi/zilo/actions/runs/41240014938/artifacts/13056783268)
is the log-only output, not package-build success.

**Requested correction:** propagate pipeline failures (explicit bash with pipefail or
equivalent), and assert expected package artifacts exist independently of log upload.
Add a negative control demonstrating a failed producer makes the workflow step fail.
