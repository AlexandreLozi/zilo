### 1. P1 — Receive-then-DELETE still needs a settled acquisition boundary

**Refs:** CONTRACT.md:809–820, 861–884; openapi.yaml:1190–1205;
author tests:64–87. Residual of r1 finding 1, interacting with the new snapshot rule.

The wire destructive flag is now terminal-only, but the normative SDK replacement
flow is not. Non-destructive export is expressly permitted on an active job, and
the SDK is told to DELETE after receiving every requested body. Nothing requires
the SDK to stop acquisition or establish that the job is terminal first.

Worked trace: an active feeder has pages 0–2; PDF export snapshots those pages;
page 3 is acquired while rendering/transferring; the SDK verifies the complete
three-page body and DELETEs the job. Page 3 is lost despite the SDK following the
specified reliable flow. An image batch has the same window. The author model
has fixed indices and no concurrent acquisition, so it cannot catch this.

**Required:** define a settled acquisition boundary before the SDK's export-and-
delete operation: require a terminal job, or cancel with pages kept and await
settlement before fixing the export selection. Do not silently delete pages
acquired after the exported snapshot. Keep active partial export non-destructive,
the receipt-ambiguous wire flag, and explicit intentional discard semantics.
Add an SDK/conformance vector with a page arriving during export; no agent/SDK
runtime test is claimed here.

### 2. P2 — Revocation frees physical-resource quotas before physical cleanup

**Refs:** CONTRACT.md:430–435, 888–895, 1006–1009, 1032;
openapi.yaml:1853–1857. Residual of r1 finding 4.

R-A12 says revoked jobs count against **no quota immediately**, while allowing
their page/temp bytes to remain for 60 seconds by default. R-X6/R-L1 promise a
user-global byte bound covering pages and export staging/output. Those rules do
not establish one physical bound: a family can fill the store, revoke, and a new
family can fill it again before the first cleanup finishes. Two fills can exceed
the 8 GiB default without breaching any counted quota. The 20/hour issuance budget
does not prevent this burst. The same exemption must not release a still-running
physical export worker's concurrency reservation prematurely.

**Required:** distinguish logical ownership quotas from physical reservations.
Keep pending-cleanup bytes/staging and unfinished work in the user-global
accounting until actually released, or reserve a separately hard-bounded cleanup
backlog included in total capacity. Preserve immediate denial and immediate SSE
close; do not delay revocation to solve accounting. Add a revoke/refill-before-
cleanup acceptance vector. Existing tests assert the presence of limit fields,
not conservation of physical resource accounting.

### 3. P2 — Final-family rollover contradicts shared-token acquisition rules

**Refs:** CONTRACT.md:376–378, 390–395, 413–415, 463–476;
openapi.yaml:417–419. Residual affecting r1 findings 2 and 3.

When the current token already expires at `familyExpiresAt`, R-A11 instructs the
client to start a new family after renewal returns 409. R-A15 instead permits a
new family **only when storage has no usable token of a live family**. The old
token is still usable. R-A9 also recommends starting a new family before a new
scan near the deadline. These are incompatible instructions, not obsolete-token
versus revoked-access wording alone.

Moreover, R-A15 specifies one shared record per origin. Replacing it with the new
family removes other tabs' recovery route to the old family's still-live jobs:
the new token receives 404 for them by design. For example, a token issued with
30 minutes of family lifetime left has `renewAfter` 22.5 minutes later; the 409
and prescribed replacement can strand old jobs 7.5 minutes before their actual
deadline. Keeping separate families isolated is correct; forgetting the old
credential is not a family-preserving rotation.

**Required:** choose one deterministic rollover policy. Either retain bounded
credentials indexed by family, with a current-family pointer and per-job family
selection through old-job disposal/deadline, or prohibit early replacement and
define how the SDK handles the nonrenewable-but-valid interval without abandoning
old jobs. Align R-A9/A10/A11/A15 and YAML. Cover two tabs, a live old job, the
final capped token, a 409, and a new scan. Storage technology remains T13's choice.

### 4. P2 — ResolutionCaps has an undeclared closed response discriminator

**Refs:** CONTRACT.md:73–90; openapi.yaml:20–25, 2192–2231, 2282–2285.
Residual of r1 finding 7.

Driver and the other rewritten response enums genuinely accept future values,
and the two-step event boundary is sound. But R-V4/YAML say the only closed
response discriminators are `Hello.scope` and known-event `type`.
`SourceCaps.resolutions.kind` is a third: the closed `ResolutionCaps.oneOf`
rejects an otherwise intact response when `kind` changes from `list` to
`future-list`. Clients cannot apply an opaque/unsupported fallback after decoding
because decoding the complete caps response already failed.

**Required:** supply an unknown resolution-capability response boundary and a
defined safe client fallback, retaining validation of known list/range payloads;
or explicitly propose this discriminator as closed and make its compatibility/
versioning exception consistent with R-V1/R-V4 and master approval. Do not claim
there are only two closed response discriminators. The new regression implements
the current open-value promise; if masters intentionally change that promise,
replace the regression with explicit coverage of the approved closed boundary,
not an unexplained relaxation or deletion.

`api/tests/t10-r2-schema.test.mjs` runs the real SourceCaps schema: **2 controls
pass; 1 open-value assertion fails**. No production behavior is inferred.

### 5. P2 — HTTPS loopback origins still enter ordinary pre-auth eligibility

**Refs:** CONTRACT.md:140–155, 165–168, 273–284, 322–332;
main DECISIONS.md D-004a revision 2:143–147. Affected consent/eligibility invariant.

R-T3's ordinary eligible class includes any well-formed HTTPS origin, including
`https://localhost:8443` and `https://127.0.0.1:8443`. The separate dev-eligible
class lists only HTTP loopback origins. Thus with the dev flag **off**, the HTTPS
examples qualify for public pre-auth CORS and the POST-consent prompt path;
only their later admission to the allowed/token tier is explicitly forbidden.
The dev flag's diagnostics-only exception is not a general HTTPS-loopback consent
exception. Current D-004a says loopback origins get no CORS and never tokens.

**Required:** exclude loopback origins from ordinary HTTPS eligibility, and
define the dev-only diagnostic exception consistently for the intended schemes,
without enabling prompts, grants or tokens. Specify the loopback-host
classification used; preserve exact serialized-origin comparison afterward.
Cover HTTP/HTTPS localhost, IPv4/IPv6 loopback, dev on/off, and baked-origin
configuration. **The explicit no-loopback-token rule is present and is not being
reported as an existing token-mint bypass.** This is a pre-auth policy mismatch.
