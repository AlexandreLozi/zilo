## Focus checks
1. Downstream stability: the surface is small and complete for list, refresh, caps and streaming
   acquisition. T12 can build `IScanBackend` from it, and T11 can map every record to the T10 wire.
   The gaps are in the error contract and the refinement rules (F1, F2), not in the types.
2. Effective settings vs caps: the snapshot-plus-delta model is clear. Its limits on what a driver may
   change are not stated (F2).
3. Finite acquisition, page lifetime and backpressure: OK. The stream is lazy with one page per
   `MoveNextAsync`, `AcquisitionLimits` must be positive, and `Page` copies its bytes and adjustments.
   Cancellation stays `OperationCanceledException`, and the tests check pre-cancel, a pending
   `MoveNext`, an early break and disposal. Release points are documented (`T11-interface.md:88-101`).
4. JobId and page index: OK. `Identifiers.cs:8` uses `\A[A-Za-z0-9_-]{16,64}\z`, which matches the
   openapi `JobId` pattern. A test covers 64-character acceptance and rejection of 65 characters and a
   trailing newline. `Page.Index` and `Sheet` are 0-based (`Acquisition.cs:115-116`), matching openapi
   `Page.index` and `sheet` (minimum 0).
5. Wire parity: `Device`, `DeviceList`/`Discovery`, `SourceCaps`, `DeviceCaps.limits`,
   `EffectiveSettings` (nullable `maxPages`), `Adjustment`, `Page` and `ScanError` map field for field
   onto openapi. Every response enum is an open string, so unknown values round-trip. An unknown
   `ResolutionCaps` kind keeps only `kind`, which matches the `ResolutionUnknown` rule to ignore every
   other field. Missing `minItems` and range guards: see F3.
6. Scaffold guard: OK. The empty-type assertion and its "temporary" comment are gone. The
   dependency-direction theory covers Core, Security and both drivers, and the restored-package
   no-NAPS2 guard is unchanged (`ScaffoldBoundaryTests.cs:37`). One weakness: see F6.

## Findings
**F1 — Medium — `docs/tasks/T11-interface.md:53-55,104-106`; `IScanBackend.cs:16`. The typed-error convention is missing for non-acquisition calls.**
Evidence: the handoff defines `ScanFailureException` only for acquisition. It names `device-busy`
only for serialized acquisition, and says "reject unsupported settings with a typed failure"
without giving a code. It never says what `GetDeviceCapsAsync` (unknown or vanished ID → T10
`not-found`; busy → `device-busy`, openapi `getDeviceCaps`), `RefreshDevicesAsync` or a pre-page
`AcquireAsync` failure throws, or which codes are allowed there (`not-found`, `device-busy`,
`disconnected`, `timeout`, `unsupported-capability` vs `invalid-settings`). T11 has to map these to
HTTP, and T12 has to produce them. Without a rule, they will diverge.
Fix (doc only): every typed backend failure is `ScanFailureException` with `PagesKept: 0` outside a
stream. Add a table of allowed codes for each method, and state that discovery timeouts become
`Discovery.IncompleteDrivers` rather than an exception.

**F2 — Medium — `T11-interface.md:43-51`; `Acquisition.cs:111-112`. Refinement limits relative to caps are unstated.**
Evidence: `Page.AppliedSettings` is a full `EffectiveSettings`, so a driver could change `Source` or
`MaxPages` in the middle of a stream (both are in `AdjustmentFieldKnown`). That would change R-J8
completion semantics under the job owner. Nothing says a refined value must stay within the source's
caps and `DeviceLimits` (for example `maxResolutionDpi`). Nothing says how it relates to the per-page
`Resolution`/`ColorMode` that R-J6 makes authoritative. A driver also only receives
`EffectiveSettings`, so it cannot fill wire `Adjustment.requested` with the user's original value.
Fix (doc only): drivers may refine only `resolution`, `colorMode`, `pageSize` and `pageSizeMm`.
`Source` and `MaxPages` are invariant. Refined values must stay within caps and limits, or the driver
fails with a typed error. `reason` is `device-applied`. `Requested` is the prior effective value, and
T11 rewrites it to the user's request when publishing.

**F3 — Low — `Capabilities.cs:8-15,37-55,71-76`; `Discovery.cs:6-13`. Records accept wire-invalid states.**
Evidence: `new ResolutionCaps("list")` (empty `values`, against openapi `minItems: 1`),
`ResolutionCaps.Unknown("list")`, and empty `ColorModes`, `PageSizes` or `Sources` (`minItems: 1`) are
all accepted. So are a non-positive `SizeMm`/`PageSize`/`SourceDefaults.Resolution` and non-positive
`DeviceLimits` values (openapi `minimum: 1`). A T12 bug would then surface as a T11 serialization error
or invalid JSON on the wire. Adding constructor guards after T12 ships is a behavioral break, so add
them now, or state that T11 validates outbound caps.

**F4 — Low — every record with an `ImmutableArray<T>` member (`DeviceList`, `Discovery`, `SourceCaps`, `DeviceCaps`, `ResolutionCaps`, `Page`).**
Evidence: synthesized record equality compares `ImmutableArray<T>` by underlying array reference, so
two structurally equal snapshots are `!=`. The handoff promises "equivalent immutable snapshots"
(`:61`). Code downstream that checks "did the list change" or asserts value equality in tests will
misbehave. Document that equality is by reference, or override `Equals`/`GetHashCode` (for example
with `SequenceEqual`).

**F5 — Low — `Acquisition.cs:7-14`. `ScanSettings.Strict` departs from the wire.**
Evidence: in openapi `strict` is on `CreateJobRequest`, not `ScanSettings`. `ScanSettings` and
`RequestedSettings` are request records owned by the upper layer and are not used by
`IScanBackend`. Drop `Strict`, or move both records to T11. Otherwise T11 inherits a shape it would
not choose.

**F6 — Low — `ScaffoldBoundaryTests.cs:20-33`. The direction check sees only references that survive compilation.**
Evidence: `GetReferencedAssemblies()` omits project references with no used types. Today both driver
assemblies reference Core in their csproj but list nothing, so a stray `ProjectReference` to
`Zilo.Agent` or `Zilo.Security` would pass. A follow-up could assert the csproj `ProjectReference`
items (or `project.assets.json`). The `Core_contains_the_neutral_contract` check is name-only and
adds little.

**F7 — Low — `T11-interface.md:59-63`; `Discovery.cs:13`. Ownership is not stated for the refresh bound and `Busy`.**
Evidence: refresh is "bounded", but `limits.discoveryTimeoutSeconds` has no Core parameter, so it
must be construction-time configuration. Say so. `Device.Busy` means "a Zilo job is active", which
is job-owner state. State that the backend reports `false`/driver-busy and T11 overlays it with `with`.
