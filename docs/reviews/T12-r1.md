## Findings

### P2-1 — Visible 1-based labels are untested (review focus 1)
`backend/src/Zilo.Drivers.Virtual/PageGenerator.cs:63-64` passes `pageIndex + 1` to the banner
(`P{n}`) and to the large page number. The code is correct. But the mutation `pageIndex + 1 → pageIndex`
at both call sites left **26/26 Virtual tests green**. The tests cover the 0-based API and QR side
(`VirtualBackendTests.cs:43,55,61,306`) but never the visible 1-based label. That split is the first
item in the plan's Review focus.
**Fix:** add a decoded-pixel assertion. Either render page index 0 and compare the `PageNumber` rect
against `BitmapFont`'s glyph for "1", or assert that the rect for index 0 differs from a
render of the glyph "0". The test should fail under the mutation above.

### P2-2 — Normal feeder exhaustion (`virtual-feeder-3`, R-J1) is untested
`VirtualScanBackend.cs:130-136` ends the stream normally once `AfterPages > 0` pages have been yielded.
Only the `AfterPages = 0` → `feeder-empty` branch is exercised (`VirtualBackendTests.cs:104-117`).
The mutation that turns the `yield break` at line 135 into a typed `feeder-empty` throw left
**26/26 green**. This is a published route in FACTORY-HANDOFF.md, and the plan's Task 3 lists the
feeder-empty variants. The test should acquire on `virtual-feeder-3` with a null completion count and a
higher `Limits.MaxPages`, then assert exactly 3 pages and normal completion with no exception.

### P3-1 — The in-flight memory guard is nominal, not a strict bound
`VirtualScanBackend.cs:302` estimates `pixels*3 + raw + 2*pngUpperBound`. The encode path also holds
the `BitWriter` doubling buffer and its `ToArray` copy (`Deflate.cs:209,213`), plus the
`MemoryStream` growth and its `ToArray` copy (`PngEncoder.cs:58,80`). For a hypothetical incompressible
Legal/600/color raster, that is about 800 MB, against the 768 MB `HardInFlightBytes`. The largest
supported request is about 546 MB by the estimate, so the guard can never trip with the current caps.
The generator's content compresses well: the author observed 2.3 MB encoded and 288 MB allocated. There
is no practical risk, but the comment ("can coexist") overstates the guarantee. Either reword it,
or size `BitWriter`/`MemoryStream` exactly from the upper bound. Non-blocking, and T20 owns aggregate policy.

### P3-2 — No cross-run decoded-pixel golden
Determinism is asserted within one process: repeated runs (`:207-221`) and concurrent runs (`:417-426`).
Layout and drawing use integer arithmetic only, so cross-run drift is unlikely. Still, one pinned SHA-256
of the decoded luma/RGB for a fixed small page (75 dpi A5) would catch drift across runtimes and OSes
without making an encoded-byte golden claim, which the plan forbids. Non-blocking.

### P3-3 — A flatbed request on a feeder-empty route reports `feeder-empty`
`VirtualScanBackend.cs:112` applies `feederCount` regardless of `Settings.Source`. A flatbed request on
`virtual-feeder-empty` therefore fails with `feeder-empty`, and on `virtual-feeder-3` the flatbed
one-page rule wins. This is harmless for test routes, but the semantics are odd. Consider limiting the
feeder count to `feeder`/`duplex`, or documenting the behaviour in FACTORY-HANDOFF. Non-blocking.

### P3-4 — Two small cleanups (non-blocking)
- `VirtualScanBackend.cs:152-154`: `PageGenerator.Layout` QR-encodes the payload, and `Generate` encodes it
  again. That is two ZXing encodes per page, which is cheap but redundant.
- Error IDs are deterministic (`{route}:{code}:{pageNumber}`, `virtual:pixel-limit`, …), but no
  test asserts `ScanError.ErrorId`. If T11 or T20 rely on them for diagnostics, pin them in one test.

## Checks requested by the coordinator

1. **Review focus 1-5.**
   - (1) API `Index`/`Sheet` and QR `page` are 0-based (`:156-158`, `PageGenerator.cs:34`), and visible labels are 1-based
     (`:63-64`). Correct, but see P2-1.
   - (2) `PageSettings` uses `\A[A-Za-z0-9_-]{16,64}\z`, identical to Core `JobId`. QR JSON is built with
     `JsonSerializer` and needs no escaping for that charset. Both bounds are exercised: 16 characters
     (`job-virtual-0001`) and 64 characters (`:224-239`). Decoded QR JSON is checked field by field for duplex × all modes (`:294-313`).
   - (3) `checked` pixel, row, raw and PNG arithmetic runs before any raster allocation (`:279-306`).
     `kept + 1` cannot overflow because `kept < Limits.MaxPages ≤ int.MaxValue`. An `int.MaxValue` request is lazy
     (`:383-391`), and the guards fail before allocation; removing `EnsurePageFits` makes `:383` fail (see item 6).
   - (4) PNG colour type and bit depth are truthful (RGB8, gray8, gray1), and decoding uses the independent
     `ZLibStream`. Colour chroma is present, bw has only 0/255 values, and duplex alternates front/back with `Sheet = kept/2`.
     Pixels match across repeat and concurrent runs (see P3-2). `AcquiredAt` comes from the injected clock, and the ETag is SHA-256
     of the bytes.
   - (5) Paper-jam, timeout and disconnect fail at page k with `PagesKept = k-1`. Pages survive backend
     disposal (`:65-82`). Slow routes use the injected `TimeProvider` (`:146`), and the tests use controlled or immediate timers.
     The only wall-clock wait in the suite is the 10 ms `CancelAfter` in the Deflate test, which is not a sleep.
2. **Cancellation and disposal.**
   - A linked token combines the caller's token with the backend lifetime token.
   - `BeginWork`/`EndWork` run under the lifecycle gate, so disposal awaits only in-progress work, never a consumer
     suspended at `yield`. `EndWork` precedes `yield return` (`:168`).
   - `DisposeAsync` is idempotent and shared. The second-call reentrant lock at `:187` is redundant but harmless.
   - Deflate polls every 256 LZ77 iterations, not byte offsets. Each iteration is bounded by 16 × 258 compares
     plus at most 258 inserts. Adler polls per 5552-byte chunk, and the encoder polls every 32 rows.
   - The remaining non-cancellable spans are bounded, roughly 100 ms or less at the maximum size: raster `Array.Fill`, CRC over IDAT, and `MemoryStream` copies.
   - There is no producer queue: one page per `MoveNextAsync`.
   - Tests cover cancellation before the first move, during a pending slow timer (the timer is disposed), shared disposal
     during pending work, and backend disposal while suspended. No race defect was found.
3. **Core seam.** Only `Zilo.Core` types are public on the acquisition path. Failures are
   `ScanFailureException(ScanError, pagesKept)` with T11a codes (`not-found`, `invalid-settings`,

   `internal`. The public additions are `VirtualScanBackend`, `VirtualBackendFactory`, `FailureVariant`,
   `FailureKind` and `VirtualDevices`, which are fixture and route data, not Core-model duplicates.
