## Verdict: `changes`

The tooling is strong. The gate fails closed and the exact-outcome wrapper catches unexpected
passes, extra denials, missing denials, count drift and invalid metadata. Every evidence claim I
could reproduce matched.

One D-010b condition is not met, though. `policy.json` carries a full approval pin for one of the
denied items, the Windows worker. On win-arm64 the denial rests only on a hardcoded producer flag
(F1). The wrapper also cannot detect a waiver for an item that is already denied (F2).

Both defects are proven by new failing tests in `spikes/naps2/tests/test_review_t02_r1.py`: 3
tests, all failing on `7e09b60`.

## Findings

### F1 · High · An allowlist pin exists for the denied Windows worker (breaks D-010b)

**Where:**
- `spikes/naps2/policy.json:472`: the `NAPS2.Sdk.Worker.Win32` pin.
- `spikes/naps2/build_policy.py:16-18`: the worker is in `FILE_INTERPRETATIONS`, so the generator
  emits that pin.
- `spikes/naps2/inventory.py:180-183`: the only thing that produces the denial.

**What is wrong:**
- The policy pins `NAPS2.Sdk.Worker.Win32@1.6.0` as `LGPL-2.1-or-later`.
- That pin carries reviewed evidence and the obligations `license-text`, `notice`, `source-offer`
  and `replaceable-dll`. That is a normal approval pin, even though `replaceable-dll` is known to
  be false for this single-file artifact.
- D-010b requires that "no suppression, waiver or allowlist entry is added". The review spec says
  "there must be no waivers or allowlist entries for the denied items".
- The worker is denied only because the gate projection in `inventory.py` hardcodes
  `separateDll=False, replaceable=False, trimmed=True, singleFile=True` for that package ID.

**Evidence, from seeded mutation M1 (scratch copy, not the worktree):**
- I flipped only the worker's `deployment` in `win-arm64.gate.json` to the compliant values and
  left the policy untouched.
- The raw gate then returns **exit 0, `passed`, 0 errors**. The win-arm64 shipping graph clears.
- On win-x64 only `NAPS2.Worker.exe` stays denied, and only because `reviewedPayloads` is empty.
- The D-010b wrapper catches this as an unexpected pass, so CI stays safe today. But T06 or any
  production reuse of `policy.json` inherits an approved worker.

**Failing tests:**
- `test_f1_denied_items_have_no_policy_allowlist_pin`
- `test_f1_worker_denial_does_not_rest_on_a_producer_flag_alone`

**Fix direction:**
- Drop the worker from `FILE_INTERPRETATIONS` and regenerate `policy.json`. The package then fails
  as "missing exact package policy pin", the same way the Gtk family fails.
- Update `EXPECTED` in `expected_gate.py` and `SP-2a.md` to match.
- Keep the deployment projection as a second, independent layer.

### F2 · Medium · The wrapper doesn't assert the "no waiver" half of D-010b

**Where:** `spikes/naps2/expected_gate.py:37-48` and `spikes/naps2/tests/test_expected_gate.py`.

**What is wrong:**
- The wrapper compares only the gate's exit code, status, counts and error multiset.
- A waiver for an item whose owner is already denied changes none of these, so it is invisible.

**Evidence, from mutation M4:**
- I added a `reviewedPayloads` entry for `NAPS2.Worker.exe` (win-x64, LGPL, a
  `docs/legal/exceptions.md` reference) to the policy.
- The wrapper still reports `expectedOutcomeMatched: true` with exit 0.
- The same applies to an `exceptions[]` entry for a package that is also denied for another reason.

So a green run does not currently prove "no suppression, waiver or allowlist entry". That is half
of what D-010b asks the workflow to guarantee.

**Failing test:** `test_f2_wrapper_rejects_a_waiver_masked_by_an_existing_denial`.

**Fix direction:** have `expected_gate.py` also assert all of the following on the policy it
passes to the gate:
- `exceptions == []`;
- `reviewedPayloads == []`;
- no `packages[]` pin for a denied identity (worker plus the seven Gtk IDs).

### F3 · Medium · CI cost and trigger scope conflict with OD-7

**Where:** `.github/workflows/spike-naps2.yml:3-8` and `:62-93`.

**What is wrong:**
- `native-smoke` runs 2 macOS jobs (billed 10×) and 2 Windows jobs (billed 2×) on **every** `push`
  to any branch and on every `pull_request` sync whose paths match.
- The matched paths include the docs-only `docs/spikes/SP-2a.md`.
- `push` and `pull_request` both fire for the same PR commit.
- There is no `concurrency` group.

OD-7 says: run the macOS matrix only where a task needs it; avoid duplicate runs; cancel
superseded runs.

**Fix direction:**
- Gate `native-smoke` behind `workflow_dispatch`, or `push` to `main` only.
- Restrict `push` to `main`.
- Add `concurrency: { group: spike-naps2-${{ github.ref }}, cancel-in-progress: true }`.
- Drop `docs/spikes/SP-2a.md` from the paths.

### F4 · Medium (likely, not executed) · Windows `native-smoke` will probably go red from CRLF checkout

**Where:**
- `spikes/naps2/inventory.py:133-135`: the first-party `Zilo.Naps2Spike` sha512 is computed over
  the raw bytes of `Naps2Spike.csproj`, `Program.cs` and `LICENSE`.
- `spikes/naps2/.gitattributes`: covers only `evidence/**`. The repository has no root
  `.gitattributes`.
- `spike-naps2.yml:90-93`: `run.py` overwrites `evidence/inventory/<rid>.gate.json`, then
  `unittest discover` runs `test_expected_gate` against it.

**Evidence:**
- With CRLF bytes, the hash no longer matches the `policy.json` pin (LF matches: True; CRLF

The assumption that hosted Windows runners check out with `core.autocrlf=true` was not verified by
running CI.

**Fix direction:** add `eol=lf` for those three files (or for `spikes/naps2/**` text), or hash
normalized text.

### F5 · Low · Evidence gaps in the worker analysis that bear on the pending D-002 and D-011 decision

**Where:** `docs/spikes/SP-2a.md:199-216`, and the `trimmed=True` assertion at `inventory.py:183`.

I checked these statically, by parsing bytes only and never executing anything:

- **The LGPL DLLs inside the bundle are not trimmed.** `NAPS2.Sdk`, `NAPS2.Escl`, `NAPS2.Images`,
  `NAPS2.Images.Gdi` and `NAPS2.Internals` are byte-identical (SHA-256) to the `lib/net10.0` entries
  in the matching 1.6.0 nupkgs. Only `Google.Protobuf.dll` (3.29.3) and
  `ICSharpCode.SharpZipLib.dll` (1.4.2) differ from their nupkgs, so they were trimmed.
  - The real D-002 blockers are therefore single-file, bundled and non-replaceable, not trimming.
  - `SP-2a.md:213` says this "would need a separate audit". It can be settled now.
  - The gate's denial text and the projection's `trimmed=True` should not imply that the LGPL DLLs
    were trimmed.
- **The worker EXE carries no Authenticode signature.** It is PE32 (i386, machine `0x14c`) and its
  security directory is `0/0`. Under D-011 it cannot ship as-is, and re-signing it changes the
  bytes. Any "unmodified, hash-pinned upstream worker" exception has to address this. SP-2a doesn't
  mention it.
- `NAPS2.Worker.dll` (assembly version 8.6.0) matches no nupkg entry. Its LGPL (SDK-side) origin
  is inferred from `NAPS2.Sdk.Worker.Build.csproj` alone, and no worker source file was captured.
  Record this as an open provenance item.

### F6 · Low · Third-party actions are pinned to mutable tags

**Where:** `spike-naps2.yml:17,18,39,40,43,54,81,82,85,98`.

`actions/checkout@v4`, `setup-python@v5`, `setup-dotnet@v4` and `upload-artifact@v4` are pinned
by tag, not by commit SHA. The spec's hygiene rule is "no network fetches without pins". The NuGet
inputs are well pinned: exact versions, locked mode, a contentHash check and `<clear/>` source
mapping. The actions are not.

### F7 · Low · CI compares regenerated evidence only through the gate outcome

**Where:** `spike-naps2.yml:46-51`.

**What is wrong:**
- `published-inventory` runs `git diff --exit-code` on `locks` but not on the regenerated
  `evidence/inventory`.
- Drift that preserves the counts and errors passes unnoticed, for example a changed restore-native
  candidate set or a changed payload kind on an approved owner.
- A byte-compare is not possible today: in my reproduction all five `.gate.json` files differed
  from the committed ones **only** in the first-party `Naps2Spike.dll` and `.pdb` hashes. Those are
  path-dependent builds without `ContinuousIntegrationBuild` or path mapping.

**Fix direction:** either make the first-party build deterministic and diff the evidence, or
document that only the gate outcome is asserted.

### 3. Licence gate: correct, apart from F1

**Default-deny** is correct:
- An unpinned package, or a mismatch on id, version, sha512 or expression, is denied.
- `allowedExpressions` is limited to bounded permissive atoms plus LGPL-2.1, matched exactly.
- Compound expressions need an exact exception.
- Unknown atoms deny.
- A null expression needs a matching file name, hash and source triple.
- LGPL needs dynamic, separate, replaceable deployment and all four obligations.
- Native and unowned payloads need an exact review keyed on RID, path, hash, kind and owner.
- NAPS2 application, Dynamsoft and ImageSharp identities are banned unconditionally.
- Duplicate JSON keys, NaN/Infinity and placeholders are rejected.

**Exceptions:** `exceptions: []` and `reviewedPayloads: []` are correct. The Gtk family has no pins.
The worker pin is the defect (F1).

**Producer trust:** the producer is trusted, and this is documented. Hash matching against ZIP
entries means that trimmed or single-file first-party output degrades to `unowned` and is denied,
which mitigates the hardcoded deployment projection.
