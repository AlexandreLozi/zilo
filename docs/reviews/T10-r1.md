## Numbered findings

### 1. P1 — Destructive export is not retry-safe; rendering cannot guarantee delivery

**Refs:** CONTRACT.md:552–588; openapi.yaml:954–962.

R-X4 and the operation promise retries/repeats and retained pages without excluding
`deleteAfterExport:true`. A completed destructive export makes the next identical request 404.
Writing the whole body at the server does not establish receipt by the SDK: the connection can
fail after server write completion but before the client obtains the complete body. Pre-rendering
also cannot satisfy R-X3’s “never returns a truncated 200” transmission guarantee.

Concrete case: SDK exports a three-page JPEG batch with the flag on the first per-page request;
the entire job is disposed before requests for pages 1 and 2. Alternatively, the server finishes
writing a PDF, disposes, and the browser reports an interrupted body; retry cannot recover it.

**Required:** scope retry guarantees to non-destructive exports; specify that pre-rendering moves
render/size failures before headers, not network failures. Mark destructive delivery as
receipt-ambiguous. SDK image batches must export every item non-destructively, receive all bodies,
then explicitly DELETE. Prefer receive-then-DELETE generally; do not claim server writes are a
client receipt acknowledgment.

### 2. P2 — Expired/superseded credentials are confused with disposed ownership

**Refs:** CONTRACT.md:255–301, 635, 682–685; openapi.yaml:299–328, 1508–1519, 1586–1611.

Renewal preserves jobs, but T1 used after its renewal grace must produce `token-revoked`, whose
SDK behavior and copy assert that the session’s pages are gone. T2 still owns those pages.
Ordinary token expiry is likewise called revoked without specifying whether it ends the ownership
family or leaves inaccessible jobs until another deadline. A shared tab holding T1 for 61 seconds
therefore falsely reports data loss after another tab rotates to T2.

The configurable timing formula also fails: `tokenTtlSeconds=300` is schema-valid, but
`renewAfter=expiresAt−900s` is already ten minutes in the past. Token expiry is not expressly
clipped to the remaining absolute ownership lifetime.

**Required:** distinguish obsolete credential recovery from actual ownership revocation/disposal;
define what plain expiry does, how a client reacquires the current shared credential, and which
failures truly mean pages are gone. Specify a valid renewal schedule for every permitted policy
value and cap token expiry by any absolute ownership deadline. Define long-lived authenticated
streams’ behavior at expiry/revocation, not only authentication at connection establishment.

### 3. P2 — Resolve the master’s shared-tab ownership decision, not origin-wide access

**Refs:** CONTRACT.md:258–269, 355–360, 830–832; openapi.yaml:218–225, 482–489;
main DISCUSSION “Master input on T10,” item 2.

The draft handoff says each tab necessarily has an independent session, while the master proposes
persisting/sharing the origin’s token so a second tab can export the first tab’s scan. In fact,
sharing the same token lineage already shares jobs under R-J1; a stable rotation lineage is not
inherently a per-tab session. “Confirm, or widen it to origin-wide ownership” is a false choice.
The master’s “revoking … disposes its jobs at TTL” also differs from immediate disposal in R-A12.

**Required:** state shared-token ownership and coordinated acquisition/renewal/revocation across
same-origin tabs explicitly; retain isolation between separately issued token families. Do not
make all credentials of an origin interchangeable. Remove or rename per-tab session assumptions;
keep bridge-session identity separate if S2 is later approved. Specify whether revocation causes
immediate logical denial with immediate physical cleanup or bounded later cleanup, and ensure
copy, retention and quotas describe that same choice. This is a master decision, not unilateral
reviewer approval of browser-storage technology.

### 4. P2 — Live session limits do not bound auth history or aggregate work

**Refs:** CONTRACT.md:263–269, 279–289, 407–417, 659–699; openapi.yaml:299–328, 1488–1515.

Repeated issue/evict or issue/revoke calls can accumulate token hashes retained for roughly a day,
even though only 16 live sessions are allowed. Renewal has no minimum interval or successor
coalescing; a grace-valid token can apparently mint arbitrarily many successors. Generic “rate
limits” in check order is not a concrete issuance/renewal budget. There is also no user-global
bound for export staging/concurrency or metadata/tombstones: per-session limits can multiply,
and the 8 GiB stored-page limit does not expressly include concurrent rendered export files.

**Required:** bounded issuance/renewal and retained-family/history policies, a defined concurrent
renewal outcome for shared tabs, and aggregate resource budgets including export temp/output
and metadata. Document the corresponding 429 responses (renewal currently lacks one). Preserve
prompt coalescing/global limits rather than treating them as limits on every other resource.

### 5. P2 — CORS and Host-first rejection have incompatible normative answers

**Refs:** CONTRACT.md:107–110, 138–148, 175–187, 304–312;
openapi.yaml:1179–1183, 1199–1202.

After removing an origin, CONTRACT requires 403/no CORS before token processing. The YAML
Unauthorized response instead permits CORS when a presented token “was issued to this origin.”
An SDK/agent pair cannot agree whether to read a 401 or use the public-consent fallback.
Separately, Host-first rejection requires a problem+json body on every request, while
PreflightDenied explicitly includes bad Host and requires no body.

**Required:** choose one post-removal CORS/check-order policy and use it throughout. Separate
Host failure from bodyless denied-origin preflight, retaining Host validation before all routes
and auth. Make any OPTIONS error-format exception explicit in R-ER1 rather than silently
contradicting “every error.”

### 6. P2 — SSE close/replay ordering loses required disposal; replayed error IDs disagree

**Refs:** CONTRACT.md:375–403, 471–495; openapi.yaml:613–614, 735–745, 2235–2239.

An active DELETE produces `cancelled`, `done`, then `disposed`, but the stream must close after
`done`. A tombstone replay must end with `disposed`, although its retained history contains a
prior `done`. The replay rule must not let implementations truncate retained history at that
earlier event. Also a retained error originating on stream A cannot keep its payload immutable
and have its `requestId` equal the HTTP request ID of reconnect stream B.

**Required:** replay all retained events in increasing sequence through a captured high-water
mark before deciding to close; define live/replay handoff and compound cancel/dispose ordering.
State when a client must reopen to observe later disposal. Define stable originating diagnostic
identity for asynchronous errors separately from each delivery’s HTTP request ID. Existing
progress coalescing/gaps are acceptable: clients must not infer lost pages from a seq gap, and
must resume from the last processed seq including unknown event envelopes they ignore.

### 7. P2 — Open response enums are still closed JSON Schema/types

**Refs:** CONTRACT.md:59–64; openapi.yaml:1614–1624, 1668–1677, 1903–1907, 2051–2171.

`x-zilo-open-enum` is only an annotation: `Driver` rejects `"future-driver"` under ordinary
JSON Schema validation. Generated TypeScript remains a closed literal union. JobEvent’s closed
oneOf likewise excludes every unknown event type despite the tolerance requirement. Source and
ColorMode are shared by request and response schemas, complicating the required distinction.

**Required:** separate strict request enums from forward-compatible response schemas/types;
provide either an unknown wire-event envelope or an explicit known-event-only decoding boundary.
Do not rely on a custom annotation the pinned generator does not implement. New regression test
`R-V4: response Driver accepts an unknown future value` fails against this HEAD.

### 8. P2 — Machine-readable response shapes do not enforce scope or effective settings

**Refs:** CONTRACT.md:43–50, 202–219, 434–439; openapi.yaml:1374–1421, 1549–1572, 1908–1941.

Hello accepts `scope:full` without version/os/arch/instanceId/limits, and `scope:public` with
all those full-only fields. This weakens both generated narrowing and the pre-auth disclosure
boundary’s contract-test coverage. A newly queued Job may omit `effective` although R-J6 says
creation already resolves it. Pending ConsentStatus may omit its polling interval/deadline;
the existing consumer smoke test even constructs that incomplete pending response.

**Required:** conditional/discriminated response schemas for known scope/state requirements;
forbid known full-only identity fields in public hello while tolerating unknown additive fields.
Require effective settings on successful creation/snapshots, and pending/cooldown data in the
appropriate consent variants. Three new scope/effective regression assertions fail at this HEAD.

### 9. P2 — Cancel/disposal and safety-bound completion have uncovered states

**Refs:** CONTRACT.md:375–399, 666–685; openapi.yaml:655–660, 1828–1833, 1895–1902.

`disposed` is explicitly not one of the three terminal scan states, so the “terminal:200;
otherwise:202” cancel rule accepts cancellation of a final tombstone that cannot transition.
The page limit also admits divergent outcomes: maxPages is always capped at the agent limit,
reaching maxPages completes, but the limits table says hitting the page safety bound fails.

**Required:** explicitly choose 200 no-op or 404 for cancel on a tombstone, without adding disposed
to DoneEvent. Distinguish caller-requested completion from safety truncation (or explicitly adopt
completion at the effective cap), including adjustments, pages kept and outcome/error reporting.

### 10. P2 — Defaults and page-size coercion are not deterministic

**Refs:** CONTRACT.md:338–346, 421–439;
openapi.yaml:1717–1776, 1803–1846, 1853–1878.

`{settings:{source:"feeder"}}` is valid, caps may omit defaults, and omitted colorMode/pageSize
have no normative fallback. For `pageSize:"banana"`, non-strict “nearest size” coercion has no
requested dimensions to compare. Even known sizes lack a distance metric/orientation/tie rule.

**Required:** provide usable source defaults or deterministic agent fallback rules for all
optional settings, resolving them before acceptance. Reject unresolvable page-size IDs with a
specified error; define any retained canonical-size coercion algorithm and custom-size validation
against customPageSize/maxAreaMm. Keep source/colorMode non-coercion and strict validation intact.

### 11. P2 — Export selection has no snapshot/empty/missing-page contract

**Refs:** CONTRACT.md:535–554, 577–583; openapi.yaml:2022–2036.

Queued zero-page PDF export, selecting index 8 when only 0–2 exist, and omitted selection while
another page arrives during rendering have no specified error or stable selection boundary.
OpenAPI also accepts JPEG/PNG with no pages or several entries, contrary to R-X2.

**Required:** snapshot the available page set at a specified validation instant; define errors
for unavailable indices and an empty effective selection. Encode the exactly-one explicit image
selection condition. Preserve list order, stable indices, clockwise rotations and immutable
source pages; these core T05 handoffs are otherwise present and appropriate.

### 12. P2 — OpenAPI response maps omit mandatory global errors

**Refs:** CONTRACT.md:165–190, 597–652; openapi.yaml:113–202, 647–701, 1160–1350.

For example, a cancellation JSON body over 64 KiB must receive 413 but cancelJob does not declare
413; issueToken likewise has a body without that response. The wrong-method 405 rule has no
machine-readable shared representation. Several operations omit globally applicable quota/errors.

**Required:** declare applicable shared global errors/default coverage in the form the intended
SDK/contract-test tooling consumes, including body size, rate limits, method rejection and
agent-unavailable behavior. Preserve RFC 9457 type/code/status/retryable/requestId consistency,
the 12 T05 codes, and CORS on readable error responses. Do not reinterpret a missing response
declaration as permission to omit the specified server guard.

### 13. P3 — TIFF quality description conflicts with lossless TIFF

**Refs:** CONTRACT.md:547–556; openapi.yaml:2037–2041.

R-X2 mandates lossless gray/color TIFF; ExportRequest.quality describes JPEG-compressed images
inside TIFF. Remove TIFF from that description and state quality is ignored for TIFF/PNG, or
explicitly revise the format decision in both files. Current PDF/TIFF/JPEG/PNG response MIME
types are otherwise correct; filename sanitization must remain mandatory.

## D-004a recommendation — amend, then approve the bounded architecture

Recommend the narrow pre-auth tier **in principle**, with the T10 contradictions/bounds corrected
before approval. Do not edit GPT’s pending approval line as a side effect of this review.

- Preserve exact Host validation, loopback-only listener, exact serialized HTTPS Origin, no
  credentials in URLs, no tokens for null/opaque/loopback origins, and origin plus token-family
  ownership on every protected job/page/event/export/cancel/dispose operation.
- Preserve public hello’s minimal product/protocol/flow-capability disclosure; valid baked origins
  still authenticate. The dev-origin flag is pre-auth-only, not a token-mint exception. Demo/E2E
  should use non-loopback HTTPS as the master confirmed.
- Keep one global open native prompt, same-origin coalescing, 3/origin/hour and 10/global/hour
  defaults, 120-second expiry, denial backoff and permanent block. Require bounded bookkeeping
  and resolve finding 4; make clear SDK user activation is not server proof of a gesture.
- Explicitly accept the residual ability of hostile HTTPS sites to consume the global prompt
  budget and infer installation/protocol. Origin rotation defeats only the per-origin budget,
  not the global bound; this is bounded harassment/starvation, not authenticated scanner access.
- Resolve check-order/CORS and public schema contradictions in findings 5/8. Do not extend
  pre-auth access to devices, page data or a future unprivileged bridge mint endpoint.

No universal transport or S1/S2 approval is recommended. D-004a architecture approval and a T10
review pass are distinct gates.
