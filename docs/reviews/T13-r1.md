## Findings

1. **P1 — Renewal failures bypass auth recovery and lost-session classification.**
   `packages/sdk/src/client.ts:300–303`, `packages/sdk/src/auth.ts:103–127`.
   Credential acquisition/renewal happens before `call()`'s recovery `try` block.
   After 46 minutes, restart the agent and read a tracked job: renewal's
   `401 token-invalid` escapes directly, instead of reading the new full hello and
   reporting `agent-restarted` (R-A10, R-R3). The same gap bypasses revocation and
   transport recovery when renewal, rather than the protected request, fails.
   Evidence: regression test 1 receives `token-invalid`, not `agent-restarted`.

2. **P1 — One tab can delete another tab's live-job credentials.**
   `packages/sdk/src/auth.ts:159–163`, `packages/sdk/src/client.ts:132–135`.
   `prune()` mutates shared family storage using only this client's tracked jobs.
   With two clients sharing one locked store, A creates a job and B rolls over;
   B deletes A's still-valid family because B does not locally track A's job.
   A then cannot reach that job even though the agent still holds it. This is an
   unsafe implementation of R-A15, independent of the storage technology chosen.
   Evidence: regression test 2 finds A's family missing from shared storage.

3. **P2 — A single new scan can roll over twice and waste issuance budget.**
   `packages/sdk/src/client.ts:417–425`, `packages/sdk/src/auth.ts:78–81`.
   `createJob()` selects a new-scan credential, then `call()` selects it again.
   With the valid policy `familyMaxSeconds = tokenTtlSeconds = 3600`, every
   freshly issued token is final; one scan therefore starts two replacement
   families instead of one. This consumes the 20/hour issuance budget twice as
   fast and can reject an otherwise permitted scan. Preserve the selected family
   through the request rather than applying rollover twice.
   Evidence: regression test 3 observes two issuances, expected one.

4. **P2 — No client teardown path stops pending detection on unload.**
   `packages/sdk/src/client.ts:472–474`, `packages/sdk/src/detection.ts:317–333`.
   `disconnect()` only revokes the current token; during pending consent there is
   no token, so it returns while the poll timer still owns the client. Granting
   consent afterwards polls, issues a token and reaches ready after disconnect.
   Repeated owner-app Load/Unload cycles can leave old clients active. Provide a
   disposal lifecycle that cancels detection and releases subscriptions, or make
   the mandatory cancel/unsubscribe composition explicit and verify it; revoking
   a credential alone is not teardown. Evidence: regression test 4 polls after
   disconnect (and the flow can authorize without another user interaction).

5. **P2 — Auth transport failures reset the overall detection cap indefinitely.**
   `packages/sdk/src/detection.ts:371` (also `254–268`).
   Each failed consent/auth attempt passes a new `Date.now()` as the recheck
   start. A reachable hello plus repeatedly failing consent never reaches the
   D-008/T05 overall cap. Preserve the original run deadline across auth retries.
   Evidence: regression test 5 remains `unreachable-or-blocked` after 5 seconds
   with a 2-second cap; expected `unreachable-stopped`.
