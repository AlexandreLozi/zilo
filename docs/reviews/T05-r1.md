## Numbered findings

1. **P2 — Complete the explicitly requested T10 copy hand-off.**
   **Locations:** `docs/design/copy.md:92-103`, `docs/design/copy.md:121-127`,
   `design/prototypes/assets/copy.js:254-333`, `docs/design/tray-agent.md:68-82`.
   **Evidence:** all twelve original error codes exist, but remain `planned`; the added-code table
   still says `_(none yet)_`. T10's hand-off (`api/CONTRACT.md:803-816` on the cited draft)
   confirms their names and explicitly requests these missing entries:
   - `consent-denied`, including the permanent `blocked: true` variant;
   - `rate-limited`;
   - `invalid-settings`;
   - `unsupported-capability`;
   - `not-found`;
   - `agent-unavailable`.
   Falling back to `unknown` loses the specific recovery instructions; in particular, a blocked
   site cannot recover with the existing "Ask again" countdown. Under proposed D-004a, design
   the tray's Block/Unblock path and the blocked web state, distinguishing permanent blocking
   from a timed denial. The current tray has only Remove/Reset and Recently denied/Forget.
   **Fix round:** add the six entries and matching states, regenerate the table, and reconcile
   the twelve confirmation markers with T10's draft status. Preserve `not-found`'s non-disclosing
   meaning: it must not reveal another origin/session's resource. This is the review task's
   required T10 follow-up, not a claim that D-004a is already in force.

2. **P2 — Define an update/consent flow that works with public `hello`.**
   **Locations:** `docs/design/detection-dialogs.md:15-26`,
   `docs/design/detection-dialogs.md:48-53`, `design/prototypes/assets/copy.js:99-111`,
   `design/prototypes/detection.html:223-228`.
   **Evidence:** the flow compares an agent version and the Update state always displays the
   installed version. Proposed D-004a hides that version before authentication; T10's explicit
   hand-off (`api/CONTRACT.md:818-821`) says to use protocol/capabilities before authorisation
   and show the version only afterward. Also, a successful `hello` does not itself open the
   native consent prompt: T10 R-A1 requires a user-initiated `POST /auth/consent`.
   **Fix round:** specify/prototype the pre-auth update variant without an invented installed
   version, the authorised variant with version, and the explicit consent request/poll/stop
   transitions. Label this reconciliation provisional until D-004a/T10 are approved.

3. **P2 — The HTTP-development consent example advertises an unusable allow path.**
   **Locations:** `docs/design/tray-agent.md:47-49`,
   `design/prototypes/assets/copy.js:349-353`, `design/prototypes/tray.html:114-115`,
   `design/prototypes/tray.html:137`, `design/prototypes/tray.html:175-188`.
   **Evidence:** the prototype shows Allow/Deny for `http://localhost:5173`, and the copy says
   "Only allow it if you are testing your own site." D-003 already requires an HTTPS public
   app. Under proposed D-004a, even the dev-flag exception only exposes pre-auth endpoints:
   loopback origins never receive tokens. T10 flags this exact unreachable copy at
   `api/CONTRACT.md:822-823` and explains the HTTPS non-loopback development setup at 826-829.
   **Fix round:** remove/clearly mark this as a non-product hypothetical, or replace it with
   an unsupported-origin state and safe HTTPS-development guidance. Do not imply that choosing
   Allow can authorise scanning from this origin.

4. **P2 — Refresh specifies discovery through a state-changing GET.**
   **Location:** `docs/design/scan-dialog.md:50`.
   **Evidence:** Refresh "Calls `devices?refresh=1`" to initiate discovery. D-004 forbids
   state-changing GETs; the T10 draft R-D1 (`api/CONTRACT.md:318-324`) distinguishes cached
   `GET /devices` from `POST /devices/refresh`. Following this UI hand-off literally would
   produce a different API and violate the existing method-safety decision.
   **Fix round:** name the POST refresh operation and subsequent list read, preserving the
   existing loading/disabled-state design.

5. **P2 — The axe matrix does not render most error banners it claims to check.**
   **Locations:** `design/prototypes/check/check.cjs:87-96`,
   `design/prototypes/scan-dialog.html:213-222`, `docs/design/accessibility.md:4-5`.
   **Evidence:** scan-dialog has no custom `matrix()`. The fallback visits each `state` once,
   then visits other controls independently. Consequently `state=error` uses only the default
   `device-busy`; combinations such as `{code: "paper-jam"}` resolve to default `state=ready`,
   so the paper-jam banner is never audited by the author's run. The reported 22 scan states
   are not every scan-time error, despite the all-states claim.
   **Fix round:** provide explicit `state=error&code=...` combinations for all ten scan-banner
   codes, keeping the two auth errors in detection. My supplemental audit of those twenty
   error/theme combinations found **zero violations**; this finding concerns reproducible
   regression coverage, not a discovered axe failure.
